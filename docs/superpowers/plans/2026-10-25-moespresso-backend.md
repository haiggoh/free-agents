# MoEspresso Backend Support Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make MoEspresso a first-class free-agents backend — provisioned automatically at install time alongside the other backends — so MoEspresso-packaged models (DeepSeek V4 IQ1 packages) can be detected, gated, and launched like any other registered model.

**Architecture:** MoEspresso joins the existing backend-manager family (`install/managers/*.py`) for provisioning, joins `LA_SERVE_BACKENDS` as a **pin-only** backend (like `omlx`/`llama_cpp`), gets its own launch branch in `local-llm-hotswap.sh` built on the oMLX symlink-farm trick for the spoof id, and is taught to `la-detect-backend.py` so an mxtq/tq_bundle artifact resolves to `moespresso` when a capable binary is present and stays `unsupported` (naming the runtime) when it is not. The 0.44.2 weight-format gate becomes *conditional* rather than absolute.

**Tech Stack:** bash (config-lib, hotswap), Python (detector, managers, tests), Homebrew taps.

**Spec:** This plan. Evidence gathered 2026-10-25 on this machine is quoted inline and in `~/.models/deepseek-v4-flash-0731-coder/`.

## Global Constraints

- MoEspresso ships through Homebrew tap **`steadfastgaze/tap`**. Formulae: `moespresso` (currently 4.0.0) and `moespresso@3` (3.0.0). Both bottles are `arm64_tahoe`.
- **Only the 3.x line loads DeepSeek V4 packages.** Measured: `4.0.0` refuses the coder package with `Error: unsupported required package feature`; the package manifest declares `required_features: ["calibration", "deepseek_v4_per_layer_experts"]`. `3.0.0` loads it (`runtime=ssd-streaming … context_limit=131072 thinking=off via=deepseek_v4_contract`). 4.0.0 self-describes as "native Qwen inference on Apple Silicon".
- **`/opt/homebrew/bin/moespresso` is the 4.0.0 symlink and is the WRONG binary for this work.** `brew install moespresso@3` succeeded but printed: "the following moespresso@3 executables are shadowed by linked moespresso commands". Any resolution by PATH name gets 4.0.0. **Resolve by keg path**, and put PATH last.
- Claude Code requires a spoof id (`claude-opus-5-5`); MoEspresso has **no** served-name/alias flag in either version, so the oMLX directory-naming precedent applies (`local-llm-hotswap.sh:503-513`).
- moespresso is a **PIN only**: never the machine MLX default, never reachable from a generic `mlx`/`auto` value.
- Version floor to bump: `0.45.0` (new backend = feature). Bump `.claude-plugin/plugin.json`, `CHANGELOG.md`, and any README/docs surface that enumerates backends. `dist/` is regenerated by `scripts/package-release.sh` — never hand-edit it.

## Review Focus

- **A user with no MoEspresso installed.** Every new path must fail with an actionable message naming the tap, never a cryptic load failure. The 0.44.2 gate's refusal message is the model.
- **A user whose `moespresso` on PATH is 4.0.0.** The wrong binary must never be selected silently; discovery order is load-bearing and needs its own test.
- **A user with 3.x installed *and* a non-MoEspresso model.** MoEspresso must not hijack ordinary MLX artifacts; detection keys on the artifact's own evidence (`weight_format`/`tq_bundle`).
- **The spoof id.** If the served name is derived from something other than the directory name, the farm trick silently 404s — the launch task must assert the advertised id, not assume it.
- **Installer idempotence.** `install-backend.sh --backend moespresso` re-run must not downgrade a working 3.x to 4.x, and `--all` must include it.

### Task 4: Launch branch in hotswap (the spoof id)

**Files:**

**Interfaces:**

- Produces: `SUCCESS_PORT=<port>`, `DISPATCH_MODEL=<spoof>`, and a `server_<port>.meta` with `backend=moespresso`.

- [ ] **Step 1: ~~Establish the fact the design rests on~~ — MEASURED 2026-10-25 with a real 3.0.0 serve on :8097.** Four facts, each verified by running it:
  1. **The spoof id is irrelevant.** `POST /v1/chat/completions` with `"model":"claude-opus-5-5"` and with `"model":"totally-made-up-name"` both generate normally, and the response **echoes back whatever name was sent**. So no symlink farm is needed — the oMLX `local-llm-hotswap.sh:503-513` trick does NOT apply here, and serving the real package dir is correct.
  2. **`GET /v1/models` does not exist** — it returns `{"error": {"message": "not found"}}`. Consequences: `wait_ready` still passes (it only requires *some* HTTP response, and MoEspresso binds the port only after `loaded (1328 tensors); serving on …`), but its `expected_id` check must be skipped; and **reuse detection breaks** — `local-llm-hotswap.sh:320` requires `CURRENT_IDS | grep -qxF "$SPOOF_PRIMARY"`, which can never match, so every launch would start a fresh 57 GB server instead of reusing a healthy one. For `serve=moespresso` the reuse condition must key on the meta file (backend + alias + model_dir + live pid) only.
  3. `_preflight_warmup` works unchanged (it posts a real completion and reads `finish_reason`; measured `length`).
  4. Server log confirms `tool_calls=on dialect=dsml(renderer) repair=on`, so the tool-parser question is a name, not a capability gap.

## Self-review against the spec

**Coverage:** provisioning (Task 1), registration/discovery (Task 2), detection (Task 3), launch (Task 4), surfaces/docs/version (Task 5). The user's two stated requirements — "everyone who installs free-agents installs all the backends" and "full backend-manager support" — map to Tasks 1–2; "make the model work" maps to Tasks 3–4.

**Known gap, deliberately not in this plan:** MoEspresso exposes no feature query, so capability is inferred from the version. An upstream `--features`/`--supports` flag would replace the version floor; a TODO in Task 3 marks it. Also out of scope: the DSpark drafter sidecar (`--drafter`) — the package declares no drafter component, so it is a later, separate piece of work.

**Proportion:** no function bodies are spelled out except where the plan fixes exact argv; each step names the file, signature, and assertions.
