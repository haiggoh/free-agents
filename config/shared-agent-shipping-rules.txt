SHIPPING AND VERIFICATION RULES — these are the mistakes free sessions actually made, measured, so they are not hypothetical. They apply whatever model you are.

RUN IT, DON'T JUST READ IT. For anything whose value is the artifact it produces — a renderer, a CLI, a build script, a generator — you have not verified it until you have EXECUTED it and looked at the output. Reading code yields hypotheses; running it yields findings. Measured: reading a diff produced a confident "double-count" bug report that a synthetic input DISPROVED, while merely running the same renderer exposed a real defect (it read a session id from the environment, which is exported into every child process, instead of from its input — so it silently priced the wrong session and printed $0.00). Never write "looks correct" about code you did not run.

A NEGATIVE RESULT NEEDS A PLANTED POSITIVE. If a check passes, or a scan finds nothing, prove the check can FAIL: change the input so it must fail, watch it fail, then change it back. Otherwise "no problems found" is indistinguishable from "the check never fired". The same discipline applies to a test you just wrote: revert the fix it covers and confirm the test goes red. A test that passes against broken code is worse than no test.

WHEN A CHECK CONTRADICTS WHAT YOU BELIEVE, SUSPECT THE CHECK FIRST. Measured twice in one session: a substring search "proved" a quoted rule was absent when it was present but wrapped across a line break, and a one-word search "confirmed" a match it had never really tested. Before reporting a surprising result, verify the instrument on a case whose answer you already know.

A FEATURE WITH NO TEST IS NOT DONE. If you add behaviour, add a test that exercises it, and mutation-check that test as above. Measured: a whole feature shipped with zero coverage, and three separate defects in it survived review because nothing executed the new paths.

VERSION AND DOCUMENT EVERY SHIPPED CHANGE, IN EVERY PLACE THE VERSION IS STATED. A version string typically lives in three or more places (a manifest, the CHANGELOG's top entry, docs, sometimes a literal in the code) and it drifts. Bump all of them, add a CHANGELOG entry that says what changed and why, and update any --help text or README the change makes untrue. Measured: a CHANGELOG announced a version the code did not declare; a published skill documented three command-line flags that did not exist and two install routes that were unsupported; a release archive did not contain the very feature the release was named for.

NEVER HARDCODE A PERSONAL PATH IN PUBLISHED CONTENT. A home directory, a machine-specific project name, or a local absolute path in a plugin, skill, README, or formula is wrong for every other reader. Write it generically.

PARSE ARGUMENTS BEFORE DOING ANY WORK. Every script must support --help and print what it does, its arguments, and any environment variables it reads. The failure to avoid is worse than a missing flag: a script that IGNORES --help and performs its real work anyway, so a user probing an unfamiliar tool triggers a download, a build, or a write. Exit non-zero with a usage line on an unrecognised flag. Verify by RUNNING the script with --help — never by grepping the source for the string.

FINISH THE SHIP LOOP, AND KNOW ITS DEPTH. Committing is not shipping. Carry a change through: verify, bump the version everywhere, commit, push, TAG, cut a RELEASE when that is how a consumer obtains it, update any package manifest that pins a version or checksum (a Homebrew formula, a lockfile), refresh the installed copy, confirm it is live, and then USE the installed copy against real state. A correct version string only proves the copy arrived, not that the feature works — live-and-inert looks identical from the version number. Do not exceed the depth you were authorised for: "you may push" does not include tagging, releasing, or publishing.

A PUBLISHED TAG OR RELEASE IS IMMUTABLE — FIX FORWARD. If you discover a defect after a tag is pushed, do NOT force-push or move the tag. Ship the correction as the next version. Rewriting published history breaks everyone who already fetched it, and a force-push is a destructive act that needs the user's explicit say-so. Similarly, never bump a documented download URL to a version whose release does not exist yet: build and publish the asset first, or the documented install route 404s.

DERIVE, DON'T DUPLICATE. When a fact must appear in two places — a file list, a version, a rate table — have the second place READ the first. A copy is a stale value waiting to happen, and when it breaks it blames the code that was correct. Measured: a test fixture carried its own copy of a build script's file list, so extending the real list made the FIXTURE fail while the build script was right.

EDIT THE SOURCE REPO, NEVER THE INSTALLED PLUGIN CACHE. A plugin's installed copy (under a path like `~/.claude/plugins/cache/<owner>/<plugin>/<version>/`) is a DERIVED artifact: the next `claude plugin update` or reinstall overwrites it wholesale, so an edit made there is silently discarded, with no error and no diff to find it by. It is also not version-controlled, so the change cannot be reviewed, tested, tagged, or shipped to anyone else. Make the change in the plugin's own git repository instead, then ship it properly and refresh the installed copy to pick it up. This has already cost real work: two bugfixes were hand-patched into a cache copy and had to be re-applied from a note afterwards.

Find the source repo rather than assuming its location: check the plugin's `homepage`/`repository` field in its `.claude-plugin/plugin.json`, look for a clone under the user's own workspace directory for local checkouts (on this machine that is `~/ClaudeWorkspace/<plugin-name>` — the name is a local convention and will differ elsewhere, so DISCOVER it, do not hardcode it), or `git clone` it fresh. If you genuinely cannot find a source repo — a third-party plugin with no local clone — then say so and ask, rather than editing the cache as a silent fallback. If a cache edit is unavoidable as a stopgap, it is not done until it is also recorded somewhere durable that names the file, the change, and the fact that an update will revert it.

The same reasoning covers any generated or installed artifact: a symlinked live copy, a build output, a regenerated config. Find the thing that WRITES it and change that, then regenerate. A hand-edit to a generated file is a change with a countdown on it.

WORK ON A FEATURE BRANCH, NOT DIRTY ON MAIN. Create a branch for the change (`git switch -c <topic>`) and keep `main` clean; do not accumulate unrelated edits in the working tree and commit them to `main` as one lump. Commit in coherent units with a message that says WHY, not just what. If work needs to happen in parallel, or the repo you are in is reached through SYMLINKS or a plugin cache, use a WORKTREE (`git worktree add ../<repo>-<topic> -b <topic>`) rather than switching the branch of the shared checkout: for such a repo the checked-out branch is effectively global state and decides which code the user actually runs, so switching it silently changes their tooling with nothing erroring. Leave a shared checkout on `main`, and put it back if a switch was unavoidable.

STAGE BY PATH, NEVER `git add -A`. `git add -A` and `git add .` clobber by CAPTURE: they stage whatever else happens to be dirty, including the user's unsaved work and files you never looked at. Name the paths you changed. Before committing, read `git status --porcelain` and `git diff --staged` and confirm every staged path is one you intended.

NEVER FORCE-PUSH, AND NEVER REWRITE PUBLISHED HISTORY, WITHOUT BEING ASKED. A force-push is destructive and needs the user's explicit say-so. It also does NOT achieve what people expect: after a rewrite the old objects remain reachable on the host, so a force-push is not a way to remove a leaked secret. If a secret was committed, say so plainly and let the user decide — do not quietly rewrite history and report it as fixed.

BACK UP UNCOMMITTED WORK BEFORE EDITING IT. Run `git status --porcelain <path>` first. Any output — untracked, or tracked-but-dirty — means copy the file somewhere timestamped BEFORE you touch it. Tracked is not the same as recoverable: a diff renders your edits and the user's unsaved work as one indivisible change, and theirs cannot be extracted from it.

REPORT WHAT HAPPENED, NOT WHAT YOU INTENDED. If a test fails, say so and show the output. If you skipped a step, say which. If a command was denied or blocked, say that rather than describing the outcome you were aiming for. Never present an assumption as a verified result, and never claim something is complete when part of it is outstanding — say plainly what is done and what is not.
